1 Summary and recommendation

The language side has little to offer ECMact today. The toolchain is already current (TypeScript 6.0.3 with erasableSyntaxOnly, Vite 8, scripts run by Node type stripping), and the ES2025 and ES2026 additions that would replace code in src/ each replace between one and eight lines and are only Baseline newly available. The web platform side is where the value is, because ECMact's first use case is a widget inside a page it does not control:

  • Scoped custom element registries became Baseline newly available on 2026-10-27. They answer a defect that this research reproduced: two bundles of ECMact on one page that both use em.Card collide, and the second one throws (section 6).
  • Trusted Types became Baseline newly available on 2026-02-24. On a host page that enforces them, the html prop cannot be used at all today: a string throws in the browser and a TrustedHTML object is replaced with an empty string by ECMact.
  • Constructable stylesheets, form-associated custom elements and Declarative Shadow DOM are now Baseline widely available. That allows sharing one parsed sheet between instances, a server-rendered placeholder for widgets, and, in a 4.0, deleting two fallbacks.
  • moveBefore() keeps focus, animations and iframes alive when a keyed row moves. It is not Baseline (no Safari), so it can only be an enhancement next to the current code.
  • View transitions (newly available 2025-10-14) fit the router as an opt-in. The Navigation API (newly available 2026-01-13) would be a rewrite with a second implementation as fallback, so not yet.
  • Not to adopt now: TypeScript 7 (the linter and the declaration build need the compiler API that 7.0 does not ship), TC39 Signals (stage 1), decorators (stage 2.7), using, Temporal and the Sanitizer API (no Safari).

Recommended order

  1. Decide the browser support rule and write it down: what may be called without a check, what needs feature detection (Q1, Q2). ECMact says "any evergreen browser" today, so every item below would otherwise be argued again. Enforce the rule for language APIs in tsconfig.json (B6).
  2. Open an issue for the collision between two copies and fix it with scoped registries where the browser has them (B1). All three test engines of the pinned Playwright have them.
  3. Let html accept TrustedHTML (A1). Small, additive, removes a hard blocker on strict hosts.
  4. Stylesheets: accept a CSSStyleSheet in css (A3) and share one parsed sheet per css text between instances (B2), measured with a new benchmark case.
  5. moveBefore() for keyed moves with the current path as fallback (B3), together with the zero-cost additions: typed command, commandfor and closedby (A2) and a tested Declarative Shadow DOM placeholder for widgets (A4).

These are recommendations. None of them is decided. Each item that the owner picks still needs its own specification and plan (F1, F2). By AGENTS.md, a breaking change of the 3.x API and a new runtime dependency are the owner's decisions; nothing recommended for 3.x here needs either.

4 Options mapped to ECMact

Three classes, as the assignment asks: (a) additive within 3.x, (b) internal rewrite with no API change, (c) needs a 4.0. Line numbers refer to the working tree of 2026-11-19 (branch feature/44-monochrome-identity; the files under src/ are unchanged on it). Verdicts are recommendations.

(a) Additive within 3.x

A1html accepts TrustedHTML do first

On a page whose CSP has require-trusted-types-for 'script', assigning a string to innerHTML throws a TypeError unless the page has a default policy (MDN). ECMact turns everything that is not a string into an empty string, so the object that would be allowed, a TrustedHTML from the host's policy, is dropped. The prop is unusable on such a host. Proposal: pass a TrustedHTML value through to innerHTML and type the prop as string | TrustedHTML.

Where
src/core/element.ts:63-65 (the typeof value === 'string' check), src/types/props.ts:135 (html?: Reactive<string>)
Platform
Trusted Types: Baseline newly available 2026-02-24 (Chrome 83, Firefox 148, Safari 26). In a browser without them no TrustedHTML object exists, so nothing changes there. lib.dom.d.ts of TypeScript 6.0.3 declares the type.
Trade-offs
Size: a few bytes, to be measured with npm run size. Complexity and risk: low. ECMact still creates no policy and sanitizes nothing; the Security model text stays true and gains one sentence.
Tests
All three engines can create a policy and a TrustedHTML. happy-dom has no trustedTypes: the branch is covered there with vi.stubGlobal('TrustedHTML', ...).

A2Typed attributes: command, commandfor, closedby do first

tags.button({ commandfor: 'menu', command: 'toggle-popover' }) is a compile error today although it works at run time, because the attribute map of button ends with the popover attributes. dialog has only open.

Where
src/types/attributes.ts:218-232 (button), src/types/attributes.ts:393 (dialog)
Platform
Invoker commands: Baseline newly available 2025-12-12. <dialog closedby>: limited (Chrome 134, Firefox 141, no Safari). There is a precedent for typing a limited value: popover: 'hint' at src/types/attributes.ts:70.
Trade-offs
Types only, no run-time bytes. Whether limited attributes are typed is question Q4. A full audit of the file against the HTML standard is a separate small task.
Tests
Type tests in tests/types/; no engine difference.

A3css accepts a CSSStyleSheet (components and widgets) do next

configure({ styles }) already takes sheets (StyleSource), the css prop and the css option of a widget take only text. Accepting a sheet lets the author parse once and share it, and lets CSS module scripts (import sheet from './x.css' with { type: 'css' }) be passed in where the browser has them.

Where
src/core/component.ts:147-150, src/widget/widget.ts:54 and :161, src/types/props.ts:179, src/render/applyStyleSheets.ts:94-108. The <style> fallback already converts a sheet to text (applyStyleSheets.ts:66-69).
Platform
Constructed stylesheets: Baseline widely available since 2025-09-27. CSS import attributes: limited (Chrome 123, Firefox 147, no Safari) - ECMact would not depend on them, it only accepts their result.
Trade-offs
Small. A sheet that the author mutates is shared by every instance that received it; that is the point, and it has to be said in the documentation. Best done together with B2.
Tests
Extends tests/browser/adopted-sheets.test.ts and the render tests; all engines.

A4A Declarative Shadow DOM placeholder for widgets: test and document do next

A host page can ship <my-widget><template shadowrootmode="open">skeleton</template></my-widget>. The browser renders the skeleton before the script loads. By MDN, attachShadow() on a host with a declarative root of the same mode clears and returns that root, so a widget should take it over when it connects. That would give a first paint without layout shift and without server-side rendering in ECMact. It may need no code, only a test in three engines and a documentation section.

Where
src/widget/widget.ts:160 (attachShadow({ mode: 'open' })) and :177 (replaceChildren)
Platform
Declarative Shadow DOM: Baseline widely available since 2026-08-20.
Trade-offs
No size cost if it already works. It is a placeholder, not hydration: the nodes are replaced. Not verified that it works today (nothing was run).
Tests
Needs a real parser, so a browser-only test; whether it joins an existing file of the closed list is part of Q5.

A5Router: opt-in view transition do next

The README lists "no transitions" among the limits of the router. Signals flush their effects synchronously (src/signals/signals.ts:172-177), so the whole DOM update of a navigation happens inside one call - exactly the callback that document.startViewTransition() wants. Proposal: an option (name to decide) on the router or on navigate; when it is on and the API exists, the history write and synchronize() run inside the transition, otherwise the current path runs.

Where
src/router/router.ts:312-314 (history write, synchronize(), scroll), :343 (back and forward), options at :88-93
Platform
Same-document view transitions: Baseline newly available 2025-10-14 (Chrome 111, Firefox 144, Safari 18).
Trade-offs
A transition snapshots the whole document. A router inside a widget would animate the host page, so the option must be off by default and described as for page-level apps. Element-scoped transitions would fit widgets but are Chrome 147 only. The promise that navigate() returns needs a defined moment to resolve. Size: to be measured.
Tests
Fallback branch in happy-dom, native in the three engines; the router file already has the WebKit history limit of D31 to respect.

A6Custom states of a component (:state()) later

A component could mirror boolean signals into ElementInternals.states, so the page styles em-card:state(open) without an attribute or class on the host.

Where
src/core/component.ts:68-69 (internals exist only with field: true)
Platform
:state(): Baseline newly available 2024-05-17; the 30-month mark was 2026-11-17 (derived).
Trade-offs
The same result is possible today with a reactive class or data-* prop on the host. Low value for the core; it belongs to the planned component collection.
Tests
happy-dom has no CustomStateSet.

A7Symbol.dispose on what has a dispose() wait

using data = resource(...) would call dispose() at the end of the block. Additive: a second key on the objects that resource(), createRouter() and store subscriptions return.

Where
src/data/resource.ts:100, src/router/router.ts:378-380, src/signals/signals.ts:378-382

(b) Internal rewrite, no API change

B1One scoped registry per copy of the library for em components do first

em.Card defines em-card in the global registry. If another bundle of ECMact on the page defined that name first, this copy skips define, creates an element of the other copy's class and calls its own init symbol on it: TypeError: element[init] is not a function (reproduced, section 6). configure({ prefix }) helps only for one-word names. With a scoped registry each copy keeps its own definitions: registry.define(name, class) and document.createElement(name, { customElementRegistry: registry }). em components are always created by ECMact, never by the HTML parser, so nothing has to be upgraded from markup. Widgets (defineWidget) stay in the global registry: the host page writes their tags.

Where
src/core/em.ts:45-51 (customElements.get, define, createElement), src/core/component.ts:24 (Symbol('ecmact.init'), one per copy), optionally src/core/component.ts:60 (attachShadow takes customElementRegistry)
Platform
Scoped custom element registries: Baseline newly available 2026-10-27 (Chrome 146, Firefox 159, Safari 26). Chromium 159, Firefox 159 and WebKit 27.2 of the pinned Playwright have them. Firefox has them only since version 159 of 2026-10-27, so the fallback will run for many users for a while.
Trade-offs
Observable differences where the scoped path runs: customElements.get('em-card') and whenDefined no longer see the component (the README does not document that they do). Tag names, selectors and the DOM tree stay the same. The fallback needs a decision: a clear error that names both copies, or a deterministic renamed tag. If the owner prefers no silent change, the same code can sit behind a configuration key, which makes it class (a) (Q3). Size: to be measured. Complexity: medium - a spike in the three engines comes first.
Tests
happy-dom has no scoped registries: fallback branch there, native branch in the three engines, plus one test that loads two copies.

B2One parsed stylesheet per css text, shared by all instances do next

Every component and widget instance creates its own CSSStyleSheet and calls replaceSync(css). A list of a thousand em.Row({ css }) parses the same text a thousand times and keeps a thousand sheets. Sharing a sheet between shadow roots is what constructable stylesheets were made for. Proposal: a cache from css text to sheet for a static css; a reactive css keeps its own sheet, because it is rewritten in place.

Where
src/render/applyStyleSheets.ts:94-100 (state.ownSheet ??= new CSSStyleSheet(), replaceSync), per-instance state at src/core/component.ts:41-46 and src/widget/widget.ts:134-139, the reactive case at src/core/component.ts:62
Platform
Constructed stylesheets: Baseline widely available since 2025-09-27. No new minimum.
Trade-offs
Speed and memory: to be measured with a new case in npm run bench (the benchmark has no component case today). Size: to be measured. Risk: code that reaches into shadowRoot.adoptedStyleSheets and edits the component's sheet would now edit it for all instances (not a documented use). The cache must not grow with generated css text: cache only what was passed as a plain string, and decide on a bound in the specification.
Tests
tests/browser/adopted-sheets.test.ts checks the number of adopted sheets, which does not change. All engines.

B3moveBefore() for rows that only move do next

fill() calls insertBefore for every row outside the longest stable run, new rows and moved rows alike. For a moved row that is a removal and an insertion: focus is lost (the reason for the restore code of #34), CSS animations and transitions restart, an iframe reloads, an open popover closes. moveBefore() moves the node without removing it and keeps that state (MDN). Proposal: use it when the parent has the method and the row is already connected under the same root, otherwise the current call.

Where

B7TypeScript 7 and isolatedDeclarations wait

TypeScript 7.0.2 (2026-07-08) is the native compiler and is latest on npm. It ships no programmatic API; 7.1 (beta 2026-10-20) brings a new and different one. The configuration of ECMact is already compatible with the 7.0 defaults (no baseUrl, no deprecated option). What blocks the move is the tooling: the installed typescript-eslint accepts typescript <6.1.0, and the declaration build goes through unplugin-dts 1.1.2, which has typescript as a peer and depends on @volar/typescript. Running 6 and 7 side by side (@typescript/typescript6) is possible, but type-checking about 7 thousand lines of source is not a bottleneck that pays for two compilers (not measured).

isolatedDeclarations (TypeScript 5.5) would let a tool without a type checker write the .d.ts files and so remove the build's need for the compiler API. A rough search finds 74 exported arrow functions in src/, about 22 with an explicit return type, so it means annotating roughly fifty exports. Worth doing only as part of the move to 7.

Where
package.json (typescript ~6.0.3), tsconfig.json, vite.config.ts:8 (dts plugin)

7 To decide

Q1 Which browsers may ECMact require without a check?

  1. Baseline widely available on the day of a release. Anything newer only behind feature detection with a fallback that gives the documented result.
  2. Baseline newly available. More features directly, but users on a browser a few months old get errors.
  3. Keep "any evergreen browser" and decide case by case.

Recommendation: A. It is a dated, checkable rule from a public dataset, it matches what the code already does for stylesheets, and it matches the build target that Vite applies to syntax.

Q2 Is raising the minimum browser version inside 3.x a breaking change?

Example: B4 would raise the HTTP client from "whatever has fetch and AbortController" to Safari 17.4. By AGENTS.md a breaking change of 3.x is the owner's decision.

  1. No, as long as the new minimum is inside the rule of Q1; it ships in a minor version and is named in the release notes.
  2. Yes; any higher minimum waits for 4.0.

Recommendation: A, and only where the change removes real code. Under B, options B4 and B5 move to class (c).

Q3 How should the collision between two copies be handled?

  1. Fix in 3.x: a scoped registry per copy where the browser has it, automatically; a clear error in the fallback.
  2. The same code behind a configuration key in 3.x, default in 4.0.
  3. Document only: a unique prefix and no shared two-word names.

Recommendation: open the issue now, run a spike in the three engines, then A if the spike shows no documented behaviour depends on the global registry, otherwise B. C leaves a run-time error in the main use case.

Q4 Are attributes that are not Baseline typed?

  1. Yes: the types follow the HTML standard; an attribute a browser does not know is ignored by it.
  2. Only Baseline attributes.

Recommendation: A. popover: 'hint' is already typed and is not Baseline.

Q5 Where are native-only paths tested?

tests/browser/ is a closed list, and a new browser-only area needs the owner's decision.

  1. Add one file for platform paths (scoped registry, moveBefore, Declarative Shadow DOM, Trusted Types, view transition) to the list.
  2. Put each test into the existing file closest to it (lifecycle, nesting, focus, adopted-sheets).
  3. Only stubs in the common tests.

Recommendation: A. One place shows which engine takes which path. C would test the stub, not the browser.

Q6 When, relative to the planned work?

  1. After the documentation redesign and the patch release, as a minor version 3.1 with steps 1-4 of the roadmap.
  2. Put A1 and A2 into the planned patch release.
  3. After the component collection.

Recommendation: A. A1 and A2 add to the API, and the README puts features into minor versions. The collision fix may go into a patch if the owner classifies it as a bug fix.

Q7 What happens to the 4.0 candidates?

  1. Record them as candidates in the decision log; no date.
  2. Plan a 4.0 around C1, C2 and C6.
  3. Drop them.

Recommendation: A. None of them gives users anything they need now, and 3.0 is recent.

Q8 TypeScript 7

  1. Stay on 6.0.x until the linter and the declaration build support 7.x.
  2. Install 7 next to 6 now and type-check with 7.

Recommendation: A.
